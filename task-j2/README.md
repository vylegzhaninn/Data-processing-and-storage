# Task J2. Синхронизированный доступ к списку

## Постановка

Родительская нить читает строки пользователя и вставляет их в **начало** связанного
списка (строки длиннее 80 символов режутся на несколько записей). Пустая строка —
вывод текущего состояния списка. Настроиваемое число дочерних нитей бесконечно
сортирует список «пузырьком» (проход всегда до конца списка) с регулируемыми
задержками **между** шагами и **внутри** шага; шаг = попытка обменять пару соседних
записей. Обмен выполняется **переустановкой ссылок**, а не обменом строк.
Блокировка всего списка запрещена; замки узлов, ближайших к голове, захватываются
первыми (защита от дедлоков). Затем собственный список заменяется на
`ArrayList` с обёрткой `Collections.synchronizedList()`, сортировка адаптируется
с сохранением задержек; теоретическое и фактическое число шагов обеих реализаций
сравнивается и объясняется.

## Запуск

```bash
cd task-j2
./gradlew run --args="--impl=own --threads=3 --delay=1000 --inside=1000"
```

* ввод непустой строки — вставка в начало списка (длиннее 80 символов — несколькими записями);
* пустая строка — печать текущего состояния списка (for-each);
* `:quit` или Ctrl+D — остановка и финальный отчёт (содержимое — в stdout, служебные сообщения — в stderr).

Параметры: `--impl=own|sync-array` (реализация списка), `--threads=N` (число
сортирующих нитей), `--delay=MS` (задержка между шагами), `--inside=MS` (задержка
внутри шага), `--demo` (измерительный прогон), `--duration=MS`, `--elements=N`.

## Схема синхронизации (own)

* `Node` — узел двусвязного списка, у каждого узла свой `ReentrantLock`;
  значение узла `final`.
* **Порядок захвата: строго от головы к хвосту** — вставка (замки головы и первого
  узла), итератор (замок курсора и следующего узла на время обращения),
  сортировщик (окно из 4 соседних узлов `prev→a→b→c`). Цикла в графе захвата нет —
  дедлоки невозможны.
* Сортировщик после паузы между шагами проверяет, что цепочка `prev→a→b→c` цела
  (`chainIntact`); если чужие обмены её разорвали — проход начинается заново.
* Задержка **между** шагами выполняется **без замков** — пользователь немедленно
  видит состояние списка; задержка **внутри** шага — под замками четвёрки узлов.
* Весь список не блокируется никогда: одновременно замкнуто не более 4 соседних узлов.
* Обмен — переустановка 6 ссылок (`prev→b→a→c`), строки в узлах не меняются.
* Вывод — стандартный `for (String s : list)`; `LinkedStringList implements Iterable`.

## Схема синхронизации (sync-array)

Шаг (чтение пары + сравнение + `Collections.swap`) атомарен под монитором
обёртки `synchronized (list)`; задержка между шагами — вне монитора; задержка
внутри шага — под монитором, то есть блокирует весь список (итерация по
`synchronizedList` тоже выполняется под ручным `synchronized (list)`, как требует
документация). Обменять ссылки нечем — меняется содержимое ячеек.

## Теоретический расчёт числа шагов

Пусть: `n` записей, `k` сортирующих нитей, задержка между шагами `b`, внутри шага
`i`, время наблюдения `T`. Один проход пузырька — `n−1` шагов (по числу пар);
проходов бесконечно много, поэтому число шагов ограничено только временем:
цикл одного шага занимает `b + i`, значит

```
шагов на нить:      T / (b + i)
суммарно все нити:  S_теор = k · T / (b + i) = k · P · (n − 1),  где P = T / ((n − 1)(b + i)) — проходов на нить
```

Теоретически **обе реализации дают одинаковое число шагов**: алгоритм, число нитей
и задержки идентичны, а сами обмены (ссылками или содержимым) пренебрежимо дешевы.
Разница появляется только из-за конкуренции за замки.

Пример (замер ниже): `k=4, T=5000 мс, b=i=50 мс` → `S_теор = 4·5000/100 = 200`.
При `i=0`: `S_теор = 4·5000/50 = 400`.

## Измерение (фактические числа, `--demo`, n=40, k=4, T=5 c)

| Реализация | `--delay` / `--inside`, мс | Теория | Факт (усреднённо за 2 прогона) |
|---|---|---|---|
| own (`LinkedStringList`)   | 50 / 50 | 200 | **126** |
| sync-array (`ArrayList`)   | 50 / 50 | 200 | **87**  |
| own (`LinkedStringList`)   | 50 / 0  | 400 | **348** |
| sync-array (`ArrayList`)   | 50 / 0  | 400 | **352** |

Воспроизведение:

```bash
./gradlew run --args="--demo --impl=own        --threads=4 --elements=40 --delay=50 --inside=50 --duration=5000"
./gradlew run --args="--demo --impl=sync-array --threads=4 --elements=40 --delay=50 --inside=50 --duration=5000"
./gradlew run --args="--demo --impl=own        --threads=4 --elements=40 --delay=50 --inside=0  --duration=5000"
./gradlew run --args="--demo --impl=sync-array --threads=4 --elements=40 --delay=50 --inside=0  --duration=5000"
```

### Объяснение результата

1. **`inside = 0`: обе реализации ≈ теория (87 %).** Недобор до 400 — накладные
   расходы на захват замков/монитора и планирование нитей; собственному списку
   дополнительно стоят перезапуски прохода после разрушенной цепочки. Гранулярность
   блокировки не имеет значения, потому что критическая секция микроскопична.
2. **`inside = 50`, sync-array: 87 ≈ потолок сериализации `T/i = 100`.** Задержка
   внутри шага выполняется под **единым монитором списка**, поэтому все 4 нити
   выстраиваются в очередь: каждый шаг занимает монитор на 50 мс, и пропускная
   способность определяется не числом нитей, а временем удержания монитора.
   Фактически 87 < 100 из-за простоев, когда все нити одновременно спят между шагами.
3. **`inside = 50`, own: 126.** «Медленный» шаг удерживает замки только 4 соседних
   узлов — нити, работающие на разных участках списка из 40 записей, идут
   параллельно и почти не мешают друг другу; недобор до 200 создаётся в основном
   встречами нитей у головы списка при старте каждого прохода и перезапусками.
4. **Вывод.** Число шагов определяется не алгоритмом (он одинаков), а тем, сколько
   времени нити проводят в очереди за замками. Мелкогранулярная блокировка
   (узел/четвёрка узлов) масштабируется по числу нитей; блокировка «одним
   монитором» превращает параллельную сортировку в последовательную: чем больше
   задержка внутри шага, тем сильнее проседает библиотечный вариант
   (4 нити работают как одна).
